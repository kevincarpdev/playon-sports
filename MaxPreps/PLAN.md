# Master Plan — Grounded NL→SQL over High-School Sports Data

Written before implementation, after a read-only recon pass over `data/sports.db`,
`SUPPORTED_QUESTIONS.md`, and all 17 recorded model responses. Everything under
**Gotchas** is verified against the data, not guessed.

---

## 1. The Business Objective

Fans ask plain-English questions; they get answers that are **correct or honestly
refused** — never confidently wrong. At MaxPreps scale (20+ years, every school, every
sport) a wrong answer is worse than no answer, because nobody can spot-check it.

So the north star is: **the model is an untrusted collaborator.** It proposes; the system
validates, executes, and decides what it is willing to say. Every layer we build has to
still make sense when the dataset is 10,000× bigger.

Three properties we optimize for, in priority order:

1. **Grounded** — every number traceable to a query we validated and ran ourselves.
2. **Honest** — ties, staleness, ambiguity, and unanswerable questions surface as such.
3. **Fast** — validation is static and cheap; execution is bounded; the expensive artifact
   (the semantic model) is loaded once and cached, not rebuilt per request.

## 3. Architecture

### Request path — one direction, no cycles

```
POST /ask  →  AskEndpoint            thin HTTP shell, maps outcome → status code
              QuestionPipeline       orchestrator, the only place that knows the order
                ├ 0 PrincipalContext role + subscription tier → RoleGrant
                ├ 1 SemanticContext  SEMANTIC_MODEL.md, read once, cached, injected
                ├ 2 CapabilityRouter complexity → model tier → TierGrant + budget
                │                    └ effective = TierGrant ∩ RoleGrant (least privilege)
                ├ 3 ILlmClient       InterpretAsync(question, semanticContext)
                ├ 4 SlotResolver     fill the intent's required slots; score each one
                │                    └ any slot missing / below threshold →
                │                      NEEDS_CLARIFICATION with selectable options
                ├ 5 IntentPolicy     refuse subjective / unanswerable intents
                ├ 6 SqlGuard         STATIC validation — never touches the DB
                ├ 7 SqlExecutor      read-only, row cap, timeout, cancellation
                ├ 8 CaveatEngine     attaches known data-quality warnings to the result
                └ 9 AskResponse      discriminated outcome, never an exception
```

### Why this shape

- **The guard is static.** Rejecting bad SQL costs no DB round-trip. That is the cheap
  path and it should be the common path when the model misbehaves.
- **The pipeline is the only sequencer.** Each stage is independently testable and
  independently swappable — a real `ILlmClient` drops in with nothing else changing.
- **The semantic model is data, not code.** One file, loaded once, injected. It is also
  the thing a real RAG layer would chunk and retrieve per-question at scale.
- **Caveats are policy, not prose.** The model's `notes` field never reaches the caller.
  Caveats are generated by our rules against our results.
- **Clarification beats guessing.** Where the question is genuinely ambiguous we ask
  instead of picking. That converts silent wrong answers into a cheap round-trip.

### Capability router — tier and tool grant, decided before the model runs

Cheap questions should not pay for deep reasoning, and a cheap model should not be handed
the expensive tools. The router scores complexity from the question and returns a
`RoutingDecision(Tier, ToolGrant, Budget)`:

| Tier | Signals | Tools granted | Budget |
|---|---|---|---|
| `Lookup` | single entity, count/lookup verb | `schema`, `scalar_query` | tightest row + time cap |
| `Aggregate` | superlative, ranking, per-game/per-season metric | + `aggregate_query` | standard cap |
| `Deep` | comparison, multi-hop, cross-sport, subjective | + `multi_query`, `compare` | widest cap |

The grant is a **ceiling, not a suggestion** — `SqlGuard` rejects SQL whose shape exceeds
the granted tools, so an escalation can't happen by accident. Tier thresholds and grants
live in config, so retuning is not a code change.

With one recorded fake model the tier does not change *which* model answers, but it does
decide the tool grant and the execution budget, and it is returned in the response so the
decision is observable and testable. A real multi-model deployment swaps one factory.

### Slot filling — the required facts an intent needs before it can be answered

Each intent declares a slot schema. A slot resolves to `Filled(value, confidence)`,
`Ambiguous(candidates)`, or `Missing`. If any **required** slot fails to reach its
threshold, the pipeline stops and returns `needs_clarification` carrying options the
caller can present as buttons.

The slots this dataset actually needs, and the real question each one rescues:

| Slot | Why it exists here |
|---|---|
| `sport` | *"Did Riverside beat Oak Hill?"* — **no** in football, **yes twice** in basketball. |
| `season` | Football `2025` and Basketball `2025-26` coexist; "this season" has no referent. |
| `entity` | *"How many points did Jackson score?"* — Jackson Prep, Jackson GA, or Tony Jackson. |
| `metric` | *"Who is the best player?"* — points? efficiency? there is no defensible default. |

`/ask` accepts previously-answered clarifications, so the loop actually closes and the
second call reaches an answer. Without that it's just a nicer error message.

### Authorization — what the *AI* is permitted to do

This is deliberately not login/session auth (the brief discounts that, and correctly). It
is **policy on the model's reach**, which is the same trust problem as SQL validation.
Identity arrives as a dev header resolved to a `Principal`; swapping in real OIDC touches
one resolver and nothing else.

Two ceilings, intersected — a request gets the **least** of what its tier and its role allow:

| Role | Reach | Rationale |
|---|---|---|
| `Anonymous` | aggregate answers only, no player-level rows | public surface |
| `Member` | + player season totals | free tier |
| `Subscriber` | + per-game stat lines, ranked lists | paid tier |
| `Analyst` | + raw stat rows, wider row cap | internal analysis |
| `Admin` | + the `ops:` intent namespace | operations |

Enforcement is where it's cheap and unbypassable: the **per-role table/column allow-list
lives inside `SqlGuard`**, the same static pass that already rejects hallucinated
identifiers. A model that emits `SELECT * FROM player_game_stats` for an `Anonymous` caller
fails validation for the same structural reason a nonexistent column does. No new code path,
no chance of forgetting the check on some branch.

**Internal vs client-facing is a namespace, not a flag.** Ops intents are prefixed `ops:`
and client roles cannot name them — an unprivileged caller asking an admin question gets
`cannot_answer`, not `forbidden`, so the tool surface isn't enumerable by probing.

Read-only ops endpoints (`/admin/rollup-freshness`, `/admin/schema`) expose the operational
truth an admin actually needs — chiefly *which rollup rows are stale*, since that is the
live data-quality defect in this dataset. A management **UI** is out of scope: there is no
frontend in this submission, and the rubric explicitly discounts it.

### Documented seams, not built (time box + "must run offline")

The brief requires the graded path to run with no keys and no network. So these are
designed and left as interfaces:

- **Vertex AI / Gemini Enterprise** — a real `ILlmClient` behind `SPORTSQA_LLM_PROVIDER`,
  falling back to the fake when unset. The interface already accommodates it; the semantic
  model is already the system-prompt payload it would receive.
- **Cloud topology** — Cloud Run for the API, Secret Manager for provider keys, the
  semantic model versioned as a build artifact so a prompt change is a reviewable diff.
- **Caching** — result cache keyed on `(normalized question, filled slots, role, schema
  version)`. Role must be in the key or a cache hit becomes a privilege escalation.

### Trust model — three gates, cheapest first

1. **Intent gate** — some intents are refused no matter what SQL came back or how
   confident the model was. `best_player` is subjective; `team_injuries` targets a table
   that does not exist. Confidence 0.88 on a hallucinated table is exactly why model
   confidence cannot be the gate.
2. **Static SQL gate** — single statement; `SELECT` only; no DDL/DML/`PRAGMA`/`ATTACH`;
   every table and column resolved against the **live schema** so hallucinated
   identifiers die before execution; a row limit is enforced, not requested.
3. **Result gate** — empty results, ties at the cut line, and rollup staleness downgrade
   an answer or convert it to a caveat.

### Scale + speed (the properties that survive 10,000×)

- Schema allow-list built from the catalog at startup → new sports/seasons need no code.
- Read-only connection, bounded rows, bounded time — one bad query can't take the API down.
- Config-driven thresholds bound to a single options record; **no literals in code**, so
  every budget is tunable per environment without a rebuild.
- Deterministic ordering enforced on every ranked query so results are stable and cacheable.
- Goldens run in CI, so a semantic-model edit that regresses an answer fails the build.

## 4. Gotchas — Verified, Not Guessed

### The model's SQL is broken in five distinct ways

| # | Question | Failure |
|---|---|---|
| 1 | Tony Jackson touchdowns | `SUM(s.touchdowns)` — **column doesn't exist**, it's `td`. Hard error. |
| 2 | Riverside injuries | `FROM injuries` — **table doesn't exist**. Confidence 0.88. |
| 3 | Did Riverside beat Oak Hill | `'Riverside AND a.school = '` — **unbalanced quote**, syntax error. |
| 4 | Did Riverside beat Oak Hill | Also checks **Riverside as home only** — misses half of all matchups. |
| 5 | Who is the best player | "Best = most points" is asserted, not derived. **Subjective.** |

### Ties make three answers nondeterministic

`LIMIT 1` on a tied ranking returns an arbitrary row and presents it as fact.

- **Most rebounds in a single game** — **52 stat lines / 34 players tie at 12**, the column's clipped ceiling.
- **Highest-scoring football game** — **two games tied at 73** (Central Valley 38–35
  Lakewood; Riverside 35–38 Lakewood).
- Any `LIMIT 5` list can split a tie at the boundary (rank 4/5 are both 211).

### The pre-aggregated rollup is stale — on exactly the players we're asked about

`player_season_totals` is refreshed by a nightly job. It is **behind** for both players in
the question set, and the model prefers it *because* it's "efficient":

| Player | Rollup | Truth from `player_game_stats` | Drift | `updated_at` vs last game |
|---|---|---|---|---|
| Marcus Bell (BB) | 165 pts / 7 GP | **232 pts / 9 GP** | −67 pts, −2 GP | 2026-02-10 vs 2026-02-24 |
| Tony Jackson (FB) | 54 pts / 5 GP | **90 pts / 7 GP** | −36 pts, −2 GP | 2025-10-10 vs 2025-10-17 |

So "Marcus Bell's PPG" is 23.57 from the rollup and **25.78** from the truth. Both queries
look reasonable. Only one is right. This is the single highest-value trap in the exercise.

### Referential integrity is not enforced

`player_game_stats.game_id` has **no foreign key**. There is exactly one orphan:
`stat_id=1033`, `player_id=160` (Silas York, Westbrook basketball), `game_id=9999` — a game
that does not exist. Consequence: a query that joins `games` to filter sport/season
**silently drops** those 12 points; one that doesn't join keeps them. Two defensible
queries, two different answers, no error either way.

### "This season" and "Riverside beat Oak Hill" are ambiguous

- Two seasons coexist: Football `2025`, Basketball `2025-26`. "This season" has no single
  referent, and several model queries omit the season filter entirely.
- **Riverside vs Oak Hill depends on the sport.** Football: Oak Hill won 24–21. Basketball:
  Riverside won *both* (100–89, 79–72). "Did Riverside beat Oak Hill?" is
  **no in football, yes twice in basketball.** A single yes/no is a wrong answer.

### "Jackson" resolves three ways

Jackson Prep (school), Jackson GA (city), Tony Jackson (player). The model silently chose
the football team. Silent entity resolution is the failure mode; the fix is to say which
one we picked and that others existed.

### Grain traps

- `teams` is one row **per school per sport** — 16 rows, 10 distinct schools. "How many
  teams" (16) and "how many schools" (10) are different questions.
- Only **120 of 160 players** have any stat line. Roster count ≠ players with stats.
- Football rows carry `points` (max 24) and basketball rows carry `points` (max 35).
  Summing `points` across sports is arithmetically fine and **semantically meaningless**.
- `player_season_totals` PK is `(player_id, season)` — **sport is not in the key**, so a
  two-sport athlete in one season string cannot be represented.
- `HAVING COUNT(DISTINCT sport) = 2` breaks the moment a third sport is added.

## 5. Response Contract

Four outcomes, plus honest metadata:

- `answered` — validated SQL, executed, data returned. Carries `caveats[]` when the data
  is imperfect but the answer stands.
- `needs_clarification` — a required slot is missing or ambiguous. Carries one or more
  clarification requests, each with selectable options and an "other" escape hatch. This
  is a **recoverable** state: answer the slot and the same question succeeds.
- `cannot_answer` — the data genuinely can't support it. Carries a machine-readable
  `reason` and what *would* be needed. Not recoverable by clarifying.
- `error` — our fault, not the user's. Never a stack trace.

The distinction between `needs_clarification` and `cannot_answer` is load-bearing: the
first means *we need more from you*, the second means *no amount of clarification helps*.
Injuries data does not exist — clarifying the sport won't conjure it.

Confidence exposed is **ours**, derived from validation, slot resolution, and result shape
— deliberately not the model's self-reported number, which we've already seen at 0.88 on a
nonexistent table.

```
answered            → 200
needs_clarification → 200  (a question, not a failure)
cannot_answer       → 422
error               → 500 with a correlation id and no internals
```

## 6. Goldens — Failure Classes to Cover

Expected values come from my own queries above, never from the model.

| # | Golden | Expected | Failure class it catches |
|---|---|---|---|
| 1 | `team-count` | 16 | Baseline sanity — the happy path works |
| 2 | `foss-passing-yards` | 2047 | Model is right; proves we don't over-block |
| 3 | `oak-hill-roster` | 12 | Grain: roster vs players-with-stats |
| 4 | `jackson-prep-wins` | 3 | Multi-condition join correctness |
| 5 | `tony-jackson-touchdowns` | **15** | Nonexistent column `touchdowns` — must not 500 |
| 6 | `marcus-bell-points` | **232**, not 165 | Stale rollup |
| 7 | `marcus-bell-ppg` | **25.78**, not 23.57 | Stale rollup, derived metric |
| 8 | `riverside-injuries` | `cannot_answer` | Nonexistent table, high model confidence |
| 9 | `best-player` | `needs_clarification` | Subjective — must ask for a metric |
| 10 | `riverside-beat-oak-hill` | `needs_clarification` | Sport ambiguity + broken SQL |
| 11 | `jackson-points` | `needs_clarification` | Entity ambiguity across 3 candidates |
| 12 | `most-rebounds-single-game` | tie at 12 | Ties reported, not one arbitrary name |
| 13 | `riverside-beat-oak-hill` + `sport=Football` | **no** (24–21 loss) | Clarification loop closes |

Golden 13 is the one that proves the slot layer is real rather than decorative: the same
question, plus a filled slot, must reach a definite answer — and that answer must be the
football result, which is the opposite of the basketball one.

## 7. How We're Using AI on This

Stated up front because it's a method, not an afterthought — and because the exercise
evaluates it.

**Authoring: narrow and directed.** I decide the component boundaries, then have AI write one
component at a time against a stated contract. Not "build the `/ask` endpoint" — instead "a
static validator taking SQL and a routing decision, resolving every identifier against this
catalog, returning allow or a coded denial."

The reason is drift. A broad prompt returns an architecture the model chose, which then has to
be reverse-engineered before it can be corrected, and by the third such prompt nobody owns the
design. Narrow prompts against chosen boundaries keep each file a single reviewable unit, so a
mistake stays local.

**Forensics before code.** Every claim about the data gets verified by a query I run and read.
AI proposes hypotheses; SQL decides which are true. This is what makes the architecture a
response to evidence rather than a guess.

**Review: a panel, not a second opinion.** The author of a design is its worst critic, and that
includes an AI that helped write it. So review is split by failure class, each model given the
slice it's strongest at and a prompt written to attack rather than assess — verification on the
most persistent model, bypass-hunting on the code-specialised one, architectural judgement on a
model from a different training lineage. Verification runs first and blocks, because a review
built on a wrong number is worse than no review.

**Delivery: the goldens gate the merge.** Including a step that corrupts a golden on purpose to
prove the suite can still fail. An optional, narrowly-scoped AI reviewer asks the one question
humans are bad at: did this diff change what an answer *means* without touching a golden?

The through-line, and it's the same as the runtime architecture: **the model proposes, a
deterministic system decides.**
